# PDPA_INCIDENT_RESPONSE.md — Drink Shop Management System (DSMS)

> **นี่ไม่ใช่คำแนะนำทางกฎหมายที่สมบูรณ์** — เป็นแผนขั้นต่ำสำหรับวางระบบตาม `DECISIONS.md` D15 และ
> `DEPLOYMENT.md` §5 เท่านั้น ก่อน deploy เข้า production จริง ต้องให้ที่ปรึกษากฎหมาย/ผู้เชี่ยวชาญ
> PDPA ตรวจสอบและปรับแผนนี้ให้เหมาะกับลักษณะธุรกิจจริงอีกครั้ง

## 1. ขอบเขต

ระบบเก็บข้อมูลส่วนบุคคลของ**พนักงาน**เท่านั้น (ชื่อ, อีเมล, ประวัติการล็อกอิน, บทบาท/สิทธิ์การใช้งาน)
ไม่เก็บข้อมูลส่วนบุคคลลูกค้า (ดู `PROJECT_SCOPE.md` — Data Minimization) แผนนี้จึงครอบคลุมเหตุการณ์ที่
กระทบข้อมูลพนักงานเป็นหลัก

**เหตุการณ์ที่นับเป็น Data Breach ตามแผนนี้** (ตัวอย่าง ไม่ใช่รายการปิด):

- Service role key / database credential รั่วไหล (เช่น ผ่าน git commit, log, หรือ client-side bundle)
- บัญชี Owner/Manager ถูกเข้าถึงโดยไม่ได้รับอนุญาต (credential ถูกขโมย/เดารหัสผ่านสำเร็จ)
- ฐานข้อมูล/backup ถูกเข้าถึงหรือ export โดยไม่ได้รับอนุญาต
- ช่องโหว่ในระบบทำให้ผู้ใช้คนหนึ่งเห็นข้อมูลส่วนบุคคลของผู้ใช้อื่นได้ (เช่น bypass RBAC)

## 2. ผู้รับผิดชอบ (กรอกให้ครบก่อน production จริง)

| บทบาท                                                      | ผู้รับผิดชอบ     | ช่องทางติดต่อฉุกเฉิน |
| ---------------------------------------------------------- | ---------------- | -------------------- |
| ผู้ตัดสินใจหลัก (Data Controller ตัวแทน)                   | _กรอกชื่อ Owner_ | _กรอกเบอร์/อีเมล_    |
| ผู้ดูแลระบบด้านเทคนิค                                      | _กรอกชื่อ_       | _กรอกเบอร์/อีเมล_    |
| ผู้ติดต่อ PDPC (สำนักงานคณะกรรมการคุ้มครองข้อมูลส่วนบุคคล) | _กรอกชื่อ_       | _กรอกเบอร์/อีเมล_    |

> ห้าม deploy เข้า production จริงจนกว่าตารางนี้จะกรอกครบ — แผนที่ไม่มีตัวบุคคลรับผิดชอบใช้งานจริงไม่ได้

## 3. ขั้นตอนเมื่อพบเหตุ (72 ชั่วโมงนับจากรู้ตัวว่ามีเหตุ ไม่ใช่นับจากเหตุเกิดขึ้นจริง)

### ชั่วโมงที่ 0–4: ควบคุมความเสียหาย (Containment)

1. หมุน (rotate) credential ที่รั่วไหลทันที — `SUPABASE_SERVICE_ROLE_KEY`, `DATABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` ผ่าน Supabase Dashboard → Settings → API
2. ถ้าบัญชีผู้ใช้ถูกเข้าถึงโดยไม่ได้รับอนุญาต: ปิดการใช้งานบัญชีนั้นทันทีที่หน้า "จัดการผู้ใช้"
   (Owner เท่านั้น) และบังคับ logout ทุก session (revoke ผ่าน Supabase Auth Dashboard)
3. บันทึกเวลา, ลักษณะเหตุการณ์, และหลักฐานเบื้องต้น (log, screenshot) ไว้ก่อนแก้ไขอะไรเพิ่ม —
   ห้ามลบ/แก้ log ที่เกี่ยวข้องจนกว่าจะประเมินผลกระทบเสร็จ

### ชั่วโมงที่ 4–24: ประเมินผลกระทบ (Assessment)

4. ระบุว่าข้อมูลของใครถูกกระทบบ้าง (รายชื่อพนักงาน) และข้อมูลประเภทใด (ชื่อ/อีเมล/ประวัติล็อกอิน/
   ข้อมูลการเงินที่ผูกกับ user เช่น เงินเดือนในรายการค่าใช้จ่าย)
5. ประเมินระดับความเสี่ยงต่อสิทธิและเสรีภาพของเจ้าของข้อมูล (สูง/กลาง/ต่ำ) — ระดับสูงหรือกลาง
   ต้องแจ้ง PDPC เสมอ (มาตรา 37(4)); ถ้าความเสี่ยงสูงต่อเจ้าของข้อมูลเอง ต้องแจ้งเจ้าของข้อมูลด้วย
6. สรุปรายงานเบื้องต้น (แม้ข้อมูลยังไม่ครบ) เพื่อเตรียมแจ้ง PDPC ให้ทันกรอบ 72 ชั่วโมง —
   กฎหมายอนุญาตให้ส่งรายงานเพิ่มเติมภายหลังได้ถ้าข้อมูล ณ ตอนนั้นยังไม่สมบูรณ์

### ชั่วโมงที่ 24–72: แจ้งหน่วยงาน/ผู้เกี่ยวข้อง (Notification)

7. แจ้ง PDPC ภายใน 72 ชั่วโมงนับจากรู้ตัว (ช่องทางแจ้งปัจจุบัน: เว็บไซต์ PDPC —
   ตรวจสอบช่องทางล่าสุดตอนเกิดเหตุจริง เพราะอาจเปลี่ยนแปลง) โดยระบุอย่างน้อย: ลักษณะเหตุการณ์,
   ประเภท/จำนวนข้อมูลที่กระทบ, ผลกระทบที่คาดว่าจะเกิด, มาตรการที่ทำไปแล้ว/จะทำต่อ
8. แจ้งพนักงานที่ได้รับผลกระทบโดยตรง (ถ้าความเสี่ยงสูง) พร้อมคำแนะนำที่ทำได้ทันที เช่น
   เปลี่ยนรหัสผ่านบัญชีอื่นที่ใช้ค่าเดียวกัน

## 4. หลังเหตุการณ์ (Post-Incident)

9. เขียนสรุปเหตุการณ์ฉบับเต็ม (root cause, timeline, ผลกระทบจริง, มาตรการแก้ไข) เก็บไว้เป็นหลักฐาน
10. ปิดช่องโหว่ที่เป็นสาเหตุ พร้อมเพิ่มเป็น regression test ตาม `TESTING.md` §7 (ห้ามแก้แล้วปิดโดยไม่มี
    test กันไม่ให้เกิดซ้ำ)
11. ทบทวนแผนนี้ทุกครั้งหลังเกิดเหตุจริง หรืออย่างน้อยปีละ 1 ครั้ง

## 5. Data Retention ที่เกี่ยวข้อง (ดู `DECISIONS.md` D17)

`sales_transactions`, `inventory_movements`, `expense_entries` และเอกสารอ้างอิงต้องเก็บอย่างน้อย 5 ปี
ตามกฎหมายบัญชี — ห้ามลบข้อมูลกลุ่มนี้แม้เป็นส่วนหนึ่งของการตอบสนองต่อ Data Breach หรือคำขอใช้สิทธิ
"ลบข้อมูล" ของพนักงาน (ใช้ soft-delete/ปิดการใช้งานบัญชีแทนเสมอ)
